# Decisions — ADR-лог

Хронологический лог решений. **Каждая запись с номером с первой же записи**: номер = max + 1,
никогда не переиспользуется (аудит: `ADR-DUP`), по нему на решение ссылаются из кода и доков.
Новое решение, отменяющее старое, не удаляет старую запись — добавляется ниже с пометкой «отменяет
ADR-NNNN». Ссылки на другие решения в заголовке — только в скобках, иначе аудит не поймёт, какой
номер — номер записи (`ADR-AMBIGUOUS`). Формат записи:

```
## ADR-NNNN — YYYY-MM-DD — Короткий заголовок решения

**Решение:** что конкретно решили (техническое описание).
**Почему:** контекст, требования, что подтолкнуло.
**Альтернативы:** что рассматривали и почему отвергли.
**Влияет на:** файлы/модули/процессы, которые нужно держать в согласии с решением.
```

ADR-0001…0010 — решения владельца из ТЗ и продуктовых решений от 27.09.2026, зафиксированы при
init. Стек, БД, кэш и CI/CD — ADR-0011…0014 (план stack-and-skeleton, 29.09).

## ADR-0001 — 2026-09-27 — Каталог по типу блюда; категории и теги — разные сущности
**Решение:** основная классификация — по типу блюда, 10 верхних категорий (закуски, салаты, супы,
вторые блюда, выпечка, десерты, напитки, соусы, заготовки, разное) с подкатегориями по мотивам
gotovim-doma (глубина до 3+). Теги — отдельная сущность. Структура редактируется из админки.
**Почему:** ТЗ §2, §4–5 и продуктовые решения: ингредиенты не являются структурой каталога.
**Альтернативы:** каталог по ингредиентам — отвергнут владельцем; копия интерфейса gotovim-doma —
запрещена ТЗ (только ориентир классификации).
**Влияет на:** `core/catalog.md`, `domain/catalog-structure.md`, модель данных, SEO-страницы.

## ADR-0002 — 2026-09-27 — Поиск: переключатель «По рецепту / По ингредиенту» с иерархией, без ИИ
**Решение:** на главной — переключатель режимов; по ингредиенту — один или несколько (И),
родитель находит потомков («сыр» → моцарелла…), конкретный тип — только себя; уточнение
категорией/тегом; автокомплит; без огромного каталога ингредиентов на главной; без ИИ.
**Почему:** приоритет №1 — максимально быстро найти конкретный рецепт, особенно с телефона.
**Альтернативы:** ИИ-поиск — избыточен при индексе (ТЗ §3, §23); «что приготовить из того, что
есть» как главный сценарий — отвергнут владельцем.
**Влияет на:** `core/search.md`, `domain/search-spec.md`, справочник ингредиентов, главная.

## ADR-0003 — 2026-09-27 — Иерархический справочник ингредиентов без брендов
**Решение:** ингредиенты — справочник с иерархией (Сыр → Моцарелла; Масло → Оливковое); в рецепте
— максимально конкретный тип, если он важен для результата; бренды и товары не храним.
**Почему:** нужно для поиска по иерархии и отдельного КБЖУ явных типов (продуктовые решения).
**Альтернативы:** плоский список / текст ингредиентов — не даёт иерархического поиска и КБЖУ;
товарные позиции — позже, как расширение.
**Влияет на:** `core/ingredients.md`, модель данных, поиск, КБЖУ, правила округления.

## ADR-0004 — 2026-09-27 — Пересчёт: неизменяемый якорь + таблица правил округления
**Решение:** коэффициент считается от якоря (порции или количество ингредиента, введённое
пользователем); якорь не меняется; остальные значения округляются по таблице правил по типу
ингредиента (можно ли, шаг, вверх/вниз, допустимое отклонение). Правила — в БД, применяются кодом;
проработать отдельным этапом ДО реализации пересчёта.
**Почему:** пересчёт должен быть кулинарно разумным (яйцо 1,4 шт. — неприемлемо), а не только
математическим; ИИ не должен решать округление каждый раз.
**Альтернативы:** чистое умножение (ТЗ §9) — уточнено владельцем; единое правило округления —
отвергнуто; ИИ на каждом пересчёте — запрещён ТЗ §9.
**Влияет на:** `core/rescaling.md`, `domain/rounding-rules.md`, КБЖУ, страница рецепта.

## ADR-0005 — 2026-09-27 — КБЖУ ориентировочно по усреднённым значениям
**Решение:** КБЖУ на 100 г хранится у типа ингредиента (усреднённо), без бренда, упаковки и точной
жирности; явный тип (моцарелла, сливочное масло) — свои значения; блюдо и порция считаются
математически при каждом пересчёте.
**Почему:** первый этап — ориентир, не диетология; вкус важнее строгих принципов.
**Альтернативы:** точные данные по продуктам/брендам — позже; ИИ-расчёт КБЖУ на лету — запрещён.
**Влияет на:** `core/ingredients.md`, модель данных, страница рецепта.

## ADR-0006 — 2026-09-27 — Публикует только владелец; ИИ создаёт только черновик
**Решение:** любой ИИ-импорт → черновик → предпросмотр → ручная правка → публикация владельцем.
Опубликованный рецепт считается проверенным владельцем.
**Почему:** ТЗ §16 и продуктовые решения — без ручного подтверждения рецепт не публикуется.
**Альтернативы:** автопубликация уверенных импортов — отвергнута.
**Влияет на:** `core/recipe-import.md`, `core/auth-publishing.md`, статусы рецепта.

## ADR-0007 — 2026-09-27 — Одна актуальная версия рецепта
**Решение:** версий и вариаций рецепта нет; правка меняет сам рецепт.
**Почему:** продуктовые решения владельца — отдельные версии не нужны.
**Альтернативы:** история версий / варианты рецепта — отвергнуты.
**Влияет на:** модель данных (без таблиц версий), админка.

## ADR-0008 — 2026-09-27 — ИИ только на входе данных; дальше — обычный код
**Решение:** ИИ: распознавание текста/голоса/изображений/PDF/Word, структурирование, первичные
категория/теги/основной ингредиент, нормализация неоднозначных единиц, перевод RU→EN. Не ИИ:
поиск, фильтрация, пересчёт порций/ингредиентов/КБЖУ, открытие страницы. Результаты ИИ
сохраняются структурированно в БД.
**Почему:** ТЗ §23 — скорость, предсказуемость, стоимость.
**Альтернативы:** ИИ в рантайме страниц/поиска — отвергнуто.
**Влияет на:** `core/architecture.md`, `core/recipe-import.md`, все расчёты.

## ADR-0009 — 2026-09-27 — RU основной, EN — автоперевод ИИ с ручной правкой
**Решение:** RU — основная версия; EN формируется ИИ при добавлении/правке, доступна в
предпросмотре и правится вручную; категории/теги — заранее заданные EN-эквиваленты; URL
`/ru/…` и `/en/…`.
**Почему:** ТЗ §17, §19 — две индексируемые языковые версии.
**Альтернативы:** ручной перевод — медленно; машинный перевод на лету — не индексируется и
нестабилен.
**Влияет на:** `core/seo-i18n.md`, модель данных (переводы), импорт.

## ADR-0010 — 2026-09-27 — Вход владельца: телефон → подтверждение в Telegram
**Решение:** админ-функции — одному/нескольким владельцам; вход по номеру телефона с
подтверждением через Telegram; посетители без аккаунтов (чтение, поиск, пересчёт, язык).
**Почему:** ТЗ §18; у владельца есть отработанная схема в sup2 (решение D10).
**Альтернативы:** email/пароль, OAuth — не требуются ТЗ.
**Влияет на:** `core/auth-publishing.md`, `core/access-and-integrations.md` (Telegram-бот).

## ADR-0011 — 2026-09-29 — Стек: Next.js 16.3 + TypeScript 6 + Drizzle/Postgres, две ветки маршрутов
**Решение:** Node 24 LTS, pnpm 12 (точная версия в `packageManager`), Next.js 16.3 App Router
(`output: "standalone"`), React 19, TypeScript 6.0 (`strict`, `noUncheckedIndexedAccess`), ESLint 9
flat на `eslint-config-next` (`eslint.config.mjs`), Tailwind 4 + shadcn/ui base-nova (заменено ADR-0015),
Zod 4, next-intl 4, Vitest 4 + Playwright. Маршруты: `app/(public)/[locale]` (ru/en, `localePrefix:
"always"`, `/` → язык браузера или `/ru`) и `app/(admin)/admin` (только RU, `noindex`) с отдельными root
layout; один `proxy.ts`. Слои: `lib/domain` — чистые функции без IO (запрет импортов — ESLint),
`lib/server` — `server-only` (БД, env, логгер). Env: публичная конфигурация запекается при сборке,
секреты читаются лениво; в production без них — явная ошибка при старте (`instrumentation-node.ts`,
разбор — `lib/server/env-schema.ts`, тест `lib/server/env.test.ts`).
**Почему:** стек владельца из sup2/sib с поправками по их граблям; критика Codex 27.09 (33 замечания).
**Альтернативы:** TS 7 — не поддерживается typescript-eslint 8.70 (peer `<6.1`); ESLint 10 / Vitest 5 —
плагины не проверены; Node 22 — EOL 04.2027; `localePrefix: "as-needed"` — противоречит ADR-0009;
Astro/Payload — отдельный рантайм или готовая админка не нужны.
**Влияет на:** весь код, `.claude/rules/code-standards.md`, `.claude/rules/ui-rules.md`, `core/architecture.md`.

## ADR-0012 — 2026-09-29 — БД и миграции: Drizzle generate + прод-мигратор с блокировкой, три роли
**Решение:** PostgreSQL 17, Drizzle ORM + postgres.js. Миграции: `drizzle-kit generate` → ревью SQL →
в проде `node migrator/migrate.mjs` (сборка `scripts/migrate.mjs`: session advisory lock, `SET ROLE
recipe_owner`; тест `scripts/db.test.ts`). `drizzle-kit push` в проде запрещён; порядок журнала проверяет
`scripts/check-migrations.mjs`. Схема меняется только expand → код → backfill → contract. Роли
(`deploy/recipe-roles.sql`): `recipe_owner` (NOLOGIN, владелец схемы), `recipe_migrator` (логин
миграций), `recipe_app` (рантайм, только DML); таймауты на ролях; веб не получает миграционный доступ.
**Почему:** в standalone-образе нет drizzle-kit; откат образа не откатывает схему; компрометация сайта
не должна давать DDL. Критика Codex 29.09.
**Альтернативы:** идемпотентный raw SQL (remlab) — второй источник истины рядом со схемой Drizzle;
одна роль на всё (sup2) — лишние права у веба.
**Влияет на:** `lib/server/db/*`, `drizzle/`, `deploy/recipe-deploy.sh`, CI, план «схема БД».

## ADR-0013 — 2026-09-29 — Кэш публичных страниц: Cache Components с тегами
**Решение:** `cacheComponents: true`, `"use cache"` + `cacheTag`; теги `recipe:{id}`, `recipes`,
`category:{id}`, `tag:{id}`, `catalog`; правка владельцем → `updateTag` (обе локали, старый и новый
slug, списки). **Проверено на каркасе (29.09):** совместимо с next-intl 4.14 через `next/root-params`
(`i18n/request.ts`) — `/ru`, `/en` собираются статически (`next build`: ○), без `setRequestLocale`;
`dynamicParams` при cacheComponents не экспортировать; `headers()`/`cookies()` в `i18n/request.ts` не
читать (сделает страницы динамическими). Прокси ставит cookie `NEXT_LOCALE` и на статических ответах —
при кэширующем CDN такие ответы не кэшировать.
**Почему:** модель кэша Next 16 определяет, как пишутся все страницы — выбирать до доменного кода.
**Альтернативы:** классический ISR — запасной путь; кэш без тегов — нет точечной инвалидации.
**Влияет на:** страницы каталога и рецепта, админку (инвалидация).

## ADR-0014 — 2026-09-29 — CI/CD: один образ из CI в GHCR, сервер сам забирает (модель sup2)
**Решение:** GitHub Actions (`.github/workflows/ci.yml`) собирает образ один раз, гоняет на нём миграции
и e2e, публикует `ghcr.io/julia15535/recipe:<sha>` и `:stable` (только текущий HEAD `main`, только при
изменении кода). Сервер: `recipe-deploy.timer` каждые 5 минут → `deploy/recipe-deploy.sh`: точка отката
до pull → миграция одноразовым контейнером → кандидат во внутренней сети → swap → smoke по SHA; упала
миграция — прод на прежней версии; кандидат не поднялся — карантин образа; smoke после swap — откат
(при нужде pull из GHCR) и карантин (`deploy/README.md`); `KillMode=process`, `9>&-` (грабли sup2). Контейнеры с лимитами CPU/RAM
и OOM-приоритетом, read-only, без capabilities. Бэкап: `pg_dump -Fc` раз в сутки на сервере ≤ 7 дней
(`deploy/recipe-db-backup.sh`) + локальная копия владельца ≤ 7 дней и еженедельное восстановление
(`deploy/local/`). Детали сервера — только `_secrets/ACCESS.md` (репо публичный).
**Почему:** просьба владельца «CI/CD как в sup2»; 1 vCPU сервера делится с соседними сервисами —
сборка на сервере недопустима; pull-модель не требует секретов в GitHub. Критика Codex 29.09 (35
замечаний: digest вместо тега, откат до pull, карантин, раздельные env).
**Альтернативы:** сборка на сервере (sup2) — отнимает CPU у соседей; push-деплой по SSH из Actions —
долгоживущий ключ к общему серверу в GitHub; `paths-ignore` — оставляет обязательную проверку висеть.
**Влияет на:** `Dockerfile`, `deploy/`, `.github/`, `core/deployment.md`.

## ADR-0015 — 2026-09-29 — Дизайн-система Untitled UI React и своя палитра «олива + персик» (отменяет UI-часть ADR-0011)
**Решение:** интерфейс — Untitled UI React (Tailwind 4 + React Aria), бесплатная MIT-часть, копия из
upstream github.com/untitleduico/react @ `4702dc0ea8d1` в `components/base|application|foundations`,
`styles/uui/*` (список и изменения — `THIRD_PARTY_NOTICES.md`). Бренд — только `styles/brand.css`:
главный цвет — олива (600 `#617122`), акцент — персик/абрикос (`accent-*`, 100 `#ffeadb`, 700
`#8b5426`), тёплые нейтрали, фон — кремовая «бумага» `#f8f2e6`, карточки — светлый крем `#fefcf6`,
основной текст — тёплый графит `#36322d`; шрифты — заголовки с засечками Lora, текст Inter через
`next/font` (`styles/fonts.ts`); кандидаты Literata и Alegreya — только на `/admin/ui`. Кнопки — `AppButton` (`components/app-button.tsx`):
44 px, форма «таблетка». Ссылки-кнопки — `components/providers/public-router-provider.tsx` (префикс
локали next-intl) и `admin-router-provider.tsx`. Иконки — Lucide.
**Решение владельца 30.09:** оставить оливу, добавить персик, кремовый фон вместо белого, графитовый
текст вместо чёрного, заголовки с засечками. Просили Fraunces — в нём нет кириллицы (русские заголовки
показались бы случайным запасным шрифтом) → Lora по умолчанию, выбор из Lora/Literata/Alegreya на
пробной странице.
**Почему:** решение владельца (29.09): система как в соседнем remlab, но из исходника upstream, без
цветов и доработок remlab; палитра с нуля, тёплая, для еды; ориентир стиля — sallysbakingaddiction.com
(фото-карточки, таблетки, пастель, дружелюбные заголовки). Контраст — WCAG AA (axe в `e2e/design.spec.ts`).
**Альтернативы:** остаться на shadcn base-nova — владелец выбрал UUI; копировать remlab — запрещено
владельцем; иконки `@untitledui/icons` — их лицензия запрещает распространение (npm пишет MIT —
противоречие), репо публичный; PRO — нельзя публиковать.
**Влияет на:** `styles/**`, `components/**`, `app/**` (все страницы), `.claude/rules/ui-rules.md`,
`THIRD_PARTY_NOTICES.md`, `e2e/design.spec.ts`.
