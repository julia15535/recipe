## Цель
У рецепта может быть одна фотография готового блюда: владелец добавляет её в кабинете с телефона или компьютера,
посетитель видит её на карточке, вверху страницы рецепта и в превью ссылки (Telegram, WhatsApp, Инстаграм).

## Источник задачи
Владелец 02.10: порядок «русский сайт → фото → английский»; 03.10 на «следующий шаг — фото блюд» — «давай».
ТЗ и бриф: «страница рецепта (одна фото)» (`product_brief.md`, `domain/recipe-model.md`: `main_image`); фото шагов и
видео — вне MVP.

## Как будет для владельца
- Кабинет → рецепт (черновик или опубликованный) → блок «Фото блюда»: «Добавить фото» → телефон предлагает «Снять
  фото / Медиатека / Файлы». Фото сразу видно в предпросмотре — и как карточка, и как верх страницы рецепта.
  «Заменить фото», «Убрать фото» (с подтверждением). У опубликованного рецепта новое фото сразу на сайте.
- Кадр: фото обрезается по центру под карточку (4:5 на телефоне, 4:3 на компьютере) и под страницу рецепта (3:2 /
  16:9) — **вопрос владельцу** ниже.
- Без фото — как сейчас: спокойная заглушка с иконкой раздела.

## Ограничения, найденные до плана
- **Общий прокси на проде пропускает запрос не больше 1 МБ** (замер 03.10: 900 КБ → 405, 1100 КБ → 413), фото с
  телефона — 3–10 МБ. Прокси общий (соседние сайты) — не трогаем. Поэтому фото **уменьшается в браузере** до
  ~2000 px по длинной стороне и < 900 КБ (JPEG), а сервер уже из него делает свои размеры.
- Контейнер сайта: 0,25 CPU и 384 МБ — обрабатываем по одному фото за раз, вход не больше ~2000 px (защита от
  «тяжёлых» файлов: `limitInputPixels`, один параллельный поток libvips).
- sup2 (`/home/pakar/igor/sup2-repo`): фото на томе хоста, сжатие отдельным контейнером imagor при загрузке, отдача
  через Route Handler с проверкой доступа; там нет поворота по EXIF и уборки «сирот», том пишется от root, был
  месячный простой из-за конфигурации imagor (их грабля №32) — берём идеи, не схему.

## Решения (критика Codex 03.10 учтена)
1. **Где хранить — в Postgres**, не файлами на томе хоста (Codex выбрал бы так же: для сотен рецептов важнее
   транзакционность, каскад и один согласованный бэкап). Таблицы: `recipe_photos` (id = uuid фото, `recipe_id`
   UNIQUE → рецепт ON DELETE CASCADE, ширина/высота) и `recipe_photo_files` (фото, вариант, реальные ширина/высота,
   тип, `bytes bytea` с `STORAGE EXTERNAL` — уже сжатое не пережимать; проверки размера каждого варианта). Почему: на
   общем сервере ничего не добавляем (ни тома, ни прав, ни правок деплоя), без «сирот», бэкап и его копия у владельца
   уже есть. Цена — размер базы и дампов: оценку (~0,5–1,1 МБ на рецепт) снять на 20–30 настоящих фото; на сервере
   18 ГБ свободно (03.10), 300 рецептов × 7 дампов ≈ 1–2,5 ГБ. Пересмотр — при гигабайтах фото. Альтернатива (том
   `/opt/recipe/media`, как sup2) — права uid 10001, атомарная запись файлов, согласованный бэкап база+файлы, уборка
   «сирот».
2. **Размеры — при загрузке:** WebP **по ширине** 480 / 960 / 1600 (без увеличения; в `srcset` — реальная ширина,
   повторы убираются) и JPEG 1200×630 для превью ссылок (обрезка по центру). Обрезка под карточку и страницу — CSS
   `object-cover` по центру (`object-position: center`), в кабинете владелец видит все варианты кадра. sharp —
   **прямая зависимость** `sharp@0.35.5` (сейчас он только косвенный у Next — `require.resolve` не находит);
   `cache(false)`, `concurrency(1)`, `limitInputPixels` ≤ 4 Мп, варианты кодируются **по очереди** (не `Promise.all`),
   цвет — sRGB, метаданные (EXIF, GPS, ICC) не сохраняются, `autoOrient()` — страховка. Оригинал не храним.
3. **Загрузка — Server Action** (`requireOwner`, встроенная проверка Origin, лимит Next 1 МБ — не повышаем: прокси
   всё равно режет 1 МБ). В браузере: `createImageBitmap` (поворот по EXIF делает он сам — без ручного поворота) →
   один canvas sRGB ≤ 2000 px, светлый фон под прозрачностью → JPEG; сначала понижается качество до разумного пола,
   потом уменьшается размер; каждая попытка — из canvas заново; не уложились в 850 КБ — отказ, а не «почти 1 МБ»;
   `bitmap.close()`, очистка canvas. Слишком большой/битый файл — понятная ошибка. На сервере заново: размер ≤ 900 КБ,
   формат по содержимому (jpeg/png/webp; SVG и прочее — отказ), **одна обработка за раз на весь сервер** (сразу
   «Подождите, загружается другое фото»), не больше 30 в час. HEIC на компьютере в Chrome не откроется — «Не
   получилось открыть фото — сохраните его как JPEG».
4. **Отдача — Route Handler** `/media/recipe/{photoId}/{вариант}`: в начале `await io()` (сборка без БД), без
   `"use cache"`; вариант — только из фиксированного списка (`480.webp`, `960.webp`, `1600.webp`, `og.jpg`), выбирается
   ровно один `bytea`. Фото опубликованного рецепта — всем: `public, max-age=30, must-revalidate`, `ETag`,
   `Content-Length`, `nosniff`; статус рецепта проверяется на каждом запросе (и перед 304). Черновик — только
   владельцу (`getOwner`, не редирект), остальным и неизвестному — одинаковый `404 no-store`. Снятый рецепт: фото
   пропадает с сервера сразу, у посетителя — не позже 30 с (как страницы, ADR-0027); уже скачанное и кэш превью в
   мессенджерах отозвать нельзя при любой схеме. Замена = новый uuid, при двух вкладках — проверка ожидаемого
   прежнего фото.
5. **Показ:** `<img srcset sizes>` с `width/height` (без прыжков страницы), `object-cover`; карточки — `loading=lazy`,
   фото на странице рецепта — `fetchpriority=high`; `alt` — название рецепта. Данные: `RecipeView.photo`,
   `CardData.photo` (id и варианты с размерами), индекс поиска — то же. OG: `openGraph.images` — `og.jpg` 1200×630.
6. **Сброс кэша сайта** — `refreshPublicSite()` после добавления, замены, удаления фото.
7. **Проверка образа:** в CI — внутри собранного образа закодировать и раскодировать тестовое фото (sharp и
   libvips для musl на месте); e2e фото — с лимитами прода (`--memory=384m --cpus=.25`), с замером времени и памяти.
   Проверка восстановления бэкапа (`deploy/local/recipe-restore-drill.sh`) — дополнительно число фото и раскодировка
   одного варианта.

## Скоуп — что входит
- Миграция 0007 (только добавление таблиц: `recipe_photos` 1:1 с рецептом, варианты `bytea` с проверкой размера) —
  expand-only, старый образ с новой схемой работает.
- `lib/server/media/` — обработка (sharp) и хранение; `lib/domain/` — чистые правила (варианты, размеры, `sizes`).
- Кабинет: блок «Фото блюда» на `/admin/recipes/[id]` (добавить, заменить, убрать; предпросмотр карточки и верха
  рецепта); уменьшение в браузере.
- Сайт: фото на карточках (главная, раздел, поиск), на странице рецепта, OG-картинка.
- Прототипы `/admin/ui` — без изменений (цветные заглушки остаются).
- Тесты: unit — обработка (EXIF-ориентации 2–8 вкл. зеркальные, P3 → sRGB, прозрачность, нет GPS/EXIF/ICC, ширины
  без увеличения, битый/обрезанный JPEG, слишком большие размеры, точные пределы байт, SVG/не-картинка — отказ); БД —
  каскад, фото черновика посторонним 404, опубликован → снят → опубликован, старый uuid после замены/удаления — 404,
  заголовки, ETag/304; e2e — фото 4000×3000 ~5 МБ уменьшается в браузере, весь запрос < 1 МБ → кабинет → сайт
  (карточка, рецепт, `og:image`) → заменить → убрать; axe, цели ≥ 44 px; проверка образа (musl); восстановление
  бэкапа с фото. **Ручная проверка владельцем на её iPhone** после выкладки (снимок с камеры, из «Медиатеки»).

## Скоуп — что НЕ входит
Несколько фото и фото шагов, видео, выбор кадра вручную (если владелец не выберет его в вопросе ниже), фото при
создании рецепта прямо в окне «Разобрать» (сначала сохранить, потом фото), распознавание рецепта по фото (ИИ-импорт),
перенос на том/внешнее хранилище, правка общего прокси.

## Вопрос владельцу
**Кадр.** А) Обрезать по центру автоматически, вы видите результат в предпросмотре и при неудаче загружаете другое
фото (рекомендую: проще, быстрее). Б) После выбора фото коснуться главного места блюда — обрезка вокруг него.
