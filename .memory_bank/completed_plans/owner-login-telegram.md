## Цель
Закрыть кабинет `/admin` (включая пробные экраны) входом через бота владельца: на сайте «Войти через
Telegram» → в Telegram у бота «Старт» → бот пишет «Вход подтверждён» → вкладка сайта сама входит. Пускать
только аккаунт владельца. Основа для следующего плана — базы рецептов (загрузка файла, правка, публикация).

## Источник задачи
Владелец, 02.10.2026: «как сделать подключение по телеграму»; бот `@mycoruja_recipes_bot` создан ею
(«Книга рецептов»), её Telegram id получен (`getUpdates`); токен и id — `_secrets/ACCESS.md`. ADR-0010
(телефон → Telegram) — уточняется новым ADR: телефон не нужен. Образец sup2 (телефон + код, webhook →
long-poll через прокси) — сложнее, чем нужно одному владельцу.

## Почему так (критика Codex 02.10, проверено)
- Старая кнопка Telegram Login Widget (`auth_date/hash`) — у Telegram в архиве; новая — OIDC (Client ID/
  Secret, PKCE, JWT) и всё равно зависит от `oauth.telegram.org` и всплывающих окон.
- Подтверждение через своего бота: без телефона, кода и внешних скриптов на сайте; личность приходит от
  Telegram в сообщении боту (`from.id`), сайт сверяет с `OWNER_TELEGRAM_ID`.
- Предпроверка 02.10: прод-сервер достаёт `api.telegram.org` (302 за 0,11 с); входящий webhook от Telegram
  — проверить при включении (`setWebhook` + `getWebhookInfo`).

## Как работает (повторная критика Codex: защита от подсунутой ссылки)
1. `/admin/login` ничего не пишет в БД. Кнопка «Войти через Telegram» — POST (Server Action, проверка
   Origin/`Sec-Fetch-Site`) создаёт вызов: случайный challenge (256 бит, 10 минут) + короткий код для глаз
   (4 цифры) и ставит cookie привязки `__Host-login_binding` (HttpOnly, Secure, SameSite=Strict, 10 минут;
   в БД — только хеши). Один активный вызов на привязку: вторая вкладка видит тот же; ограничение частоты
   создания вызовов (и общее — от засорения БД).
2. Страница показывает код «4821», кнопку `t.me/mycoruja_recipes_bot?start=<challenge>` и QR-код этой ссылки
   (вход на компьютере — подтверждение с телефона).
3. Владелец в Telegram жмёт «Старт» → бот: «Запрос на вход в кабинет. Код 4821. Подтвердите, только если
   видите этот код на своём экране» + кнопки «Подтвердить» / «Это не я». Только «Подтвердить»
   (`callback_query`) от `OWNER_TELEGRAM_ID` в личном чате атомарно помечает вызов «подтверждён» —
   подсунутая чужая ссылка покажет чужой код, которого нет у владельца на экране (остаётся риск обычного
   фишинга — она предупреждена текстом).
4. Вкладка раз в 2 с (и сразу при возврате на вкладку) спрашивает статус **по cookie привязки** (challenge
   как пропуск не принимается); при «подтверждён» — атомарно «использован», выдаётся **новая** сессия,
   cookie привязки удаляется, переход в `/admin`; обе вкладки оказываются в кабинете. Сессия не выдаётся по
   ссылке из Telegram — вход завершается там, где начат.

## Webhook
- `POST /api/telegram/webhook`: неверный `X-Telegram-Bot-Api-Secret-Token` → 401; только личный чат,
  только `message` с `/start <challenge>` и `callback_query` подтверждения; предел размера тела; таблица
  `telegram_updates` (`update_id` UNIQUE), запись `update_id` и смена статуса вызова — одной транзакцией;
  дубликат / неизвестный / просроченный / посторонний update → 200 (без повторов от Telegram); ошибка БД →
  5xx (Telegram повторит). Сырые updates не логируются.
- Ответы бота: просрочено — «Откройте вход на сайте заново»; неверный формат — короткая инструкция; чужой
  аккаунт — общий отказ без подробностей; сбой — «Попробуйте позже». Отправка ответа — «по возможности»: её
  ошибка не отменяет подтверждения. `allowed_updates: ["message", "callback_query"]`.
- Запасной long-poll — только если webhook на практике не доходит (не делаем заранее).

## Сессии и защита
- `owner_sessions`: `id uuid`, `token_hash bytea UNIQUE` (SHA-256 токена 256 бит), `telegram_id bigint`,
  `created_at`, `expires_at` (ровно 30 дней), `revoked_at`; без записи при каждом показе страницы.
  Cookie `__Host-owner_session`: HttpOnly, Secure, SameSite=Lax, Path=/, без Domain, срок = сроку в БД.
- `owner_login_challenges`: `challenge_hash`, `binding_hash`, код для глаз, статус, `telegram_id`, сроки;
  `telegram_updates` (обработанные `update_id`); уборка просроченного.
- `requireOwner()` (`lib/server/auth/`): сессия жива, не отозвана, `telegram_id` = текущему
  `OWNER_TELEGRAM_ID` (смена владельца в env сразу закрывает старые сессии). Вызывается в каждом чтении
  закрытых данных и в каждом действии; layout `(protected)` — только перенаправление на `/admin/login`.
  `proxy.ts` авторизацию не делает (только «оптимистичный» 307 на вход без cookie сессии — см. лог).
- Весь `/admin` (и пробные экраны `/admin/ui`) — под `(protected)`; открыт только `/admin/login`.
- Выход — Server Action (проверка Origin в Next) + `requireOwner()`; GET-выхода нет.
- CSP для `/admin` — строгая, с nonce (в `proxy.ts` только для `/admin`, без авторизации); весь `/admin`
  полностью динамический (`await connection()` в корневом layout админки — nonce несовместим с PPR при
  Cache Components); проверка e2e (прямой заход и переходы по `/admin/ui`, загрузка JS/CSS, нет нарушений
  CSP в консоли) → сразу включённая политика (Report-Only без сборщика отчётов бесполезен); внешних
  источников не нужно. `Cache-Control: no-store`,
  `Referrer-Policy: no-referrer` на страницах входа.
- Логи: не писать тела Telegram-обновлений, вызовы, cookie, хеши; расширить маскирование (`challenge`,
  `hash`, `code`, `state`, `nonce`, `update`).

### Уроки
- Вход по `/start` без кнопки — login CSRF; Login Widget в архиве (anti-patterns №28).
- Потоковый кабинет (CSP с nonce) отдаёт redirect/notFound с кодом 200 — 307 в proxy (№23).
- Лимит должен срабатывать до работы с БД; посторонних от публичного бота в БД не писать (№29).
- Импорт из `e2e/` в файлах сборки ломает образ в CI (№30); свой лимит по IP ломает повторные e2e (№26).
- Запись на прод (`web.env`) авторежим агенту не даёт — только с явного разрешения владельца.
